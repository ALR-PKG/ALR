# Архитектурный разбор: каталог сборки, мультиюзер, привилегии

Ветка: `arch/build-dir-multiuser`. Статус: анализ, код не меняется.

Исходная проблема: сборка пакета (Rust/Tauri) забила `/tmp` целиком —
на типичной системе `/tmp` это tmpfs в оперативной памяти (половина RAM),
компилятору некуда писать → `os error 28` → падение rustc (SIGSEGV как следствие).
Заодно разбираем две смежные оси: многопользовательское использование
и модель привилегий.

---

## 1. Как сейчас устроены каталоги

| Путь | Назначение | Права |
|------|-----------|-------|
| `/tmp/alr/pkgs/<pkg>` | рабочее дерево сборки (`src/`, `pkg/`) **и** кэш готового пакета | `root:wheel 2775` |
| `/tmp/alr/dl/<sha256(url)>` | общий кэш скачанных исходников | то же |
| `/var/cache/alr/repo` | клоны репозиториев | `root:wheel 2775` |
| `/var/cache/alr/alr.db` | SQLite-БД пакетов | общая |
| `/etc/alr/alr.toml` | системный конфиг | root |
| `~/.config/alr/alr.toml` | пользовательский конфиг | пользователь |

Ключевые точки в коде:

- `internal/constants/constants.go:23` — `TempDir = "/tmp/alr"`, компайл-тайм
  константа. Не `os.TempDir()`, `TMPDIR` игнорируется.
- `internal/build/dirs.go:61-84` — layout сборки поверх `Paths.PkgsDir`.
- `internal/build/source_downloader.go:80` + `pkg/dlcache/dlcache.go` — кэш
  скачиваний в том же tmpfs; файлы попадают в `src/` жёсткими ссылками.
- Очистки нет: `internal/build/utils.go:51-77` чистит `src/`/`pkg/` только
  перед пересборкой; готовый пакет остаётся как кэш «уже собрано»
  (`internal/build/cache.go:33-56`). Полная очистка — только ручной
  `alr fix` (`cmd/fix.go:101-111`, `rm -rf /tmp/alr`).
- Переопределить каталог нельзя: ни ключа конфига (`pkg/types/config.go`),
  ни env (`internal/config/env_config.go:41-50`).

### Главная ловушка для рефакторинга

Путь `/tmp/alr` используется как **строковый префикс-триггер** привилегированной
обработки: `internal/fsutils/dirs.go:29-30` и `pkg/dlcache/dlcache_prod.go:32`
сравнивают префикс литералом. Любой другой каталог молча потеряет механику
прав `root:group 2775`. Поэтому «просто уважать TMPDIR» недостаточно — нужна
единая конфигурация путей, отвязанная от литералов.

## 2. Конфликты и отсутствие блокировок

- Блокировок нет вообще (ни flock, ни lock-файлов) — только внутрипроцессные
  мьютексы.
- Пути детерминированы по имени пакета: два процесса, собирающие один пакет,
  работают в одном `/tmp/alr/pkgs/<pkg>`; `prepareDirs` одного (`os.RemoveAll`)
  вычищает дерево из-под другого.
- `dlcache.New` (`pkg/dlcache/dlcache.go:56-62`) при пересоздании сносит
  существующий каталог кэша — один пользователь удаляет кэш другого.
- `alr fix` любого пользователя делает `rm -rf /tmp/alr` — стирает чужие
  незавершённые сборки.
- SQLite при параллельной записи — только file-locking SQLite, busy-timeout
  не настраивается (`internal/db/db.go:69-94`).

## 3. Модель привилегий

Текущая схема — «пользователь из wheel/sudo + sudo-обёртки»:

- `internal/utils/utils.go:72-99` — команды требуют root или членство в
  wheel/sudo (детект по дистрибутиву, `internal/fsutils/privileged_group.go`).
- `internal/manager/common.go:28-51` — пакетный менеджер всегда через `sudo`
  (захардкожено, `rootCmd` из конфига игнорируется).
- `internal/fsutils/dirs.go:60-65` — каждое создание каталога под `/tmp/alr`
  и `/var/cache/alr` от обычного пользователя = до трёх вызовов `sudo`
  (mkdir/chmod/chown). Хрупко: требует интерактивного sudo, ломается в
  скриптах и GUI.
- `internal/fsutils/group_access.go` — нормализация прав общего кэша после
  pull работает только под root; от обычного пользователя — молчаливый no-op.
  Т.е. корректность мультиюзер-кэша периодически зависит от случайных
  root-запусков.

### D-Bus демон — самое слабое место

- Демон (`alr _internal-dbus-service`, systemd-юнит `configs/dbus/`) работает
  **под root** на system bus.
- Политика `configs/dbus/ru.alr-pkg.ALR.conf` разрешает `send_destination`
  **всем** пользователям.
- `internal/dbus/package.go:389-394` — `checkAuthorization()` это TODO-заглушка,
  всегда `return nil`. Install/Remove доступны любому локальному пользователю.
- Polkit-слой написан (`internal/dbus/policykit.go`, actions
  `ru.alr-pkg.install/remove/build/...`), но **не подключён**: subject
  формируется из pid/uid самого демона, а не вызывающего, и нигде
  не вызывается.
- Итог: любой пользователь системы может инициировать установку/удаление
  пакетов и сборку произвольных скриптов репозитория под root. Для
  мультиюзер-модели это критичный блокер.

## 4. Изоляция и лимиты

- Изоляции сборки нет: `internal/build/firejail.go` — это интеграция firejail
  в **устанавливаемый пакет**, а не сандбокс сборки. Скрипты `build()/package()`
  исполняются с полным доступом к ФС и TTY.
- Лимитов ресурсов нет: ни проверки свободного места перед сборкой, ни
  rlimit/cgroup, ни контроля размера `/tmp/alr`.
- `CI=true` — скрытый третий режим: отключает проверку привилегий, sudo и
  установку прав. Любая новая модель должна учитывать его.

## 5. Варианты целевой архитектуры

### Ось A: где собирать

**A1. Конфигурируемый build dir (минимум).**
Новый ключ `build_dir` в конфиге (дефолт — не tmpfs, например
`/var/cache/alr/build` или `~/.cache/alr/build`), уважение `TMPDIR` как
фолбэка, единая точка `config.Paths`, рефакторинг триггеров прав
с литеральных префиксов на явный признак «общий каталог».
Плюс: проверка свободного места перед сборкой (Statfs) с понятной ошибкой.

**A2. Разделение build dir и package cache.**
Рабочее дерево — per-build временное (и удаляемое после сборки), готовые
пакеты — в `/var/cache/alr/pkgs`. Снимает двойную роль `/tmp/alr/pkgs` и
проблему «кэш лежит в tmpfs».

### Ось B: модель привилегий

**B1. Выделенная группа `alr` (вместо wheel).**
Установщик создаёт группу `alr`, общие каталоги `root:alr 2775`.
Привилегированные операции по-прежнему через sudo, но не «весь wheel».

**B2. Root-демон-строитель (D-Bus) + polkit.**
Все привилегированные операции идут через демон; CLI — тонкий клиент.
Обязательные условия: подключить polkit (subject вызывающего, не демона),
авторизация по action. Минус: сборка под root в общей площадке требует
изоляции (per-job каталоги, лимиты), иначе риск выше текущего.

**B3. Гибрид (рекомендуется).**
Сборка — от пользователя в его каталоге (per-user подкаталоги или per-user
build dir), установка — через sudo (как сейчас) или демон с polkit (для GUI).
Общими остаются только read-mostly данные: клоны реп, БД, dlcache —
с выделенной группой `alr` и flock на запись.

### Ось C: конкурентность

- flock на каталог пакета при сборке (`<builddir>/<pkg>.lock`).
- flock на pull репозитория и на запись в БД (или busy-timeout в SQLite).
- `alr fix` — очистка только своих/осиротевших каталогов, не `rm -rf` всего.

## 6. Предлагаемый порядок работ

1. Конфигурируемый `build_dir` + отвязка от литеральных префиксов (A1) —
   закрывает исходную проблему с tmpfs.
2. Проверка свободного места перед сборкой с человекочитаемой ошибкой.
3. flock на сборку пакета и на pull (C) — дёшево, снимает гонки.
4. Разделение build dir и package cache (A2).
5. Выделенная группа `alr` (B1).
6. Подключение polkit в D-Bus демоне (B2) — отдельной задачей, до любого
   расширения роли демона.

## 7. Сравнение вариантов build dir

### Вариант A: общий `/var/cache/alr/build` (root:alr 2775)

**Плюсы:**
- Общие `src/` и кэши компиляторов (cargo `target/` и пр.) — повторная сборка
  того же пакета другим пользователем идёт инкрементально, в разы быстрее;
  одна копия на диске вместо N.
- Кэш готовых пакетов лежит рядом — минимальные изменения логики
  `CheckForBuiltPackage`.
- Демон-строитель (root) и CLI собирают в одну площадку — GUI и CLI
  переиспользуют результаты друг друга.
- dlcache и srcdir гарантированно на одной ФС → жёсткие ссылки работают.

**Минусы:**
- Каждая запись пользователя в общий каталог требует привилегированной
  механики: сейчас это до 3 вызовов `sudo` на каталог (`fsutils/dirs.go`) —
  надо заменять на группу `alr` + setgid, и добавлять пользователей в группу.
- Доверие: любой член группы может подменить чужое дерево сборки →
  собранный пакет ставится под root. Сегодня это «весь wheel», с выделенной
  группой круг шире. Лечится per-user подкаталогами внутри общего корня —
  но тогда шаринг сборочных кэшей между пользователями пропадает.
- Гонки за один и тот же `<pkg>` между пользователями — обязательны локи.
- Нужна сборка мусора: осиротевшие деревья копятся на системном разделе,
  у пользователя нет прав их удалить (чужие) — нужен GC демоном или fix с sudo.
- `/var` на части систем маленький (VPS с 20-40 ГБ корнем) — сборка Rust/Tauri
  в 8-15 ГБ может не влезть.

### Вариант B: per-user `~/.cache/alr/build`

**Плюсы:**
- Сборке вообще не нужны привилегии: пользователь владеет своим каталогом —
  уходят sudo-вызовы на создание каталогов и вся групповая механика
  для build-пути.
- Естественная изоляция между пользователями: нет гонок и подмены чужих
  деревьев; доверие к кэшу «свой» по построению.
- Соответствует XDG; пользователь сам управляет своей квотой и очисткой.
- Домашний раздел обычно самый большой.

**Минусы:**
- Дублирование: N пользователей, собирающих один тяжёлый пакет = N копий
  исходников, кэшей и результатов.
- Если dlcache остаётся общим (`/var/cache/alr` на другой ФС), жёсткие ссылки
  не работают → копирование (код уже имеет фолбэк `linkOrCopy`, но это
  время и место). Альтернатива — dlcache тоже per-user: ещё больше дублей.
- Демон (root) не может переиспользовать пользовательские каталоги — у
  демона своя площадка; GUI и CLI не делят результаты.
- Home бывает на NFS — сборка на сетевой ФС мучительно медленная.

### Вариант C: гибрид

- Рабочее дерево сборки — per-user (`~/.cache/alr/build/<pkg>`), изолировано.
- dlcache скачиваний — общий (`/var/cache/alr/dl`, read-mostly, группа `alr`),
  с фолбэком link→copy при разных ФС.
- Кэш готовых пакетов — per-user (см. раздел 8).
- Демон-строитель — со своим системным build dir (`/var/cache/alr/build`),
  потому что root не может писать в чужие home.

**Итог:** C покрывает минусы A и B ценой двух механизмов путей
(пользовательский и системный режимы) — по сути, это уже существующее
раздвоение «CLI vs демон», формализованное явно.

## 8. Кэш «уже собрано»: плюсы/минусы и привязка к варианту build dir

**Зачем сохранять:** тяжёлые сборки (Rust/Tauri) идут десятки минут;
переустановка, откат через `repo set-ref`, установка нескольких пакетов с
общей зависимостью — всё это без кэша пересобирает с нуля.

**Цена на диске (в отличие от tmpfs, который сам чистится при ребуте):**
- Неконтролируемый рост — нужна политика GC (по возрасту/размеру/команде).
- Риск протухания: ключ кэша — имя-версия-релиз файла
  (`internal/build/cache.go:33-56`); если `alr.sh` изменился без бампа
  версии, из кэша подсунется старый пакет. На диске это живёт вечно,
  в tmpfs самоустранялось ребутом.

**Привязка к выбору build dir:**

| Кэш пакетов | + общий build (A) | + per-user build (B/C) |
|---|---|---|
| Общий | Максимум экономии, но любой член группы может подложить пакет, который другой поставит под root — **вектор privesc** | Не ложится: у пользователя нет прав писать в общий кэш без привилегий |
| Per-user | Не ложится: дерево общее | Доверенный по построению, но дублирование места между пользователями |
| Без кэша | Всегда пересборка — честно, но медленно для Rust/Tauri | То же |

**Разумная середина (при варианте C):**
- CLI: per-user кэш в `~/.cache/alr/pkgs` — доверенный, чистится самим
  пользователем.
- Демон: системный кэш в `/var/cache/alr/pkgs`, собранное демоном (root)
  считается доверенным для всех.
- GC: `alr fix` чистит только свой кэш; опционально TTL по atime.
- Дополнительно (дёшево): включать хэш `alr.sh` в ключ кэша или в
  метаданные — снимает проблему протухания.

## 9. Целевая модель (согласовано)

Уточнения от владельца:

1. sudo нужен **не для доступа к кэшу**, а для проверки прав на установку
   пакетов в систему. `alr build` вообще не должен требовать привилегий.
2. Требования: а) кэш, ускоряющий сборку/пересборку; б) мультиюзерность
   с безопасностью; в) устанавливать пакеты может только член wheel/sudo.
3. Сборка в рамках `alr install` должна идти по быстрому пути (с кэшем),
   но результат `alr build` **не доверен никому, кроме собравшего**, потому
   что может собираться не root'ом.

### Принципы

- **P1.** sudo — только для операций с системой (установка/удаление пакетов
  пакетным менеджером, запись в `/etc`, `/usr`). Никогда — для сборки и
  для доступа к кэшам.
- **P2.** Доверие результату сборки определяется тем, кто собрал:
  root (демон) → доверено всем; пользователь → только ему самому.
- **P3.** Сборка всегда идёт от непривилегированного пользователя
  (CLI — от вызвавшего, демон — отдельный вопрос, см. ниже).
- **P4.** Установка в систему — только членам wheel/sudo (CLI) или по
  polkit action (демон/GUI).

### Модель по командам

**`alr build`** — ноль привилегий:
- `CheckUserPrivileges` из build убирается (сейчас `cmd/build.go:49`
  требует wheel — это и есть баг модели).
- Дерево сборки: `~/.cache/alr/build/<pkg>`, результат: `~/.cache/alr/pkgs`.
- Результат помечается как пользовательский (владелец файла = uid
  пользователя — уже есть по факту, отдельной метки не нужно).

**`alr install`** — сборка + установка:
- Проверка членства wheel/sudo остаётся, но перед фазой **установки**,
  а не сборки.
- Сборка — от пользователя в его per-user дереве (как `alr build`).
- Поиск готового пакета (ускорение): сначала per-user кэш, затем системный
  кэш `/var/cache/alr/pkgs`. Доверие — по владельцу файла: свой или
  root-собранный → ставим; чужой пользовательский → пересобираем.
- Установка — через sudo к пакетному менеджеру (как сейчас).

**Демон (GUI, `feature/api-for-gui` уже в master):**
- Собирает в системной площадке `/var/cache/alr/build`, результат в
  системный кэш `/var/cache/alr/pkgs` — доверен для всех (P2).
- **Обязательное предусловие: подключить polkit** — сейчас
  `checkAuthorization()` заглушка, а «доверенный кэш» через неавторизованный
  демон = privesc для любого пользователя. Subject — вызывающий
  (uid/pid из D-Bus credentials), не демон.
- Открытый вопрос: собирает ли демон под root (проще, но скрипты репо
  исполняются под root — риск) или под выделенным непривилегированным
  пользователем `alr-build` (безопаснее; тогда «доверие» = владелец
  `alr-build`, а установку выполняет демон как root).

**Кэш скачиваний (dlcache):**
- Целостность гарантируется checksums из `alr.sh` (подмена файла в кэше
  ловится сверкой хэша при сборке) → общий кэш безопасен по целостности.
- Вариант: общий `/var/cache/alr/dl` с группой `alr` (2775, setgid) —
  запись без sudo за счёт членства в группе. Членство в `alr` даёт только
  шаринг скачиваний, не прав установки.
- Фолбэк без группы: per-user `~/.cache/alr/dl` (дублирование, но ноль
  настройки).

### Что меняется относительно текущего кода

- `/tmp/alr` уходит; префикс-триггеры (`fsutils/dirs.go:30`,
  `dlcache_prod.go:32`) заменяются явной конфигурацией путей
  (per-user — `os.UserCacheDir()`, системный — константа/конфиг).
- `alr build` перестаёт требовать wheel.
- `CheckForBuiltPackage` проверяет владельца файла-кэша (self или root /
  выделенный builder), иначе — пересборка.
- `alr fix` чистит только свой кэш; системный — только root/демон.
- flock на `<pkg>.lock` в дереве сборки; у демона — внутренняя очередь.
- D-Bus: polkit с subject вызывающего — до любого использования
  демоном доверенного кэша.
